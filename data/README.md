# Synthetic Demand History — Zolve AI Feature 3

> **Synthetic prototype data — not real customer bookings.**
> For SIH prototype/testing only. Do NOT insert into `public.bookings`.

## Purpose

Current real booking history in Supabase (`public.bookings`) is insufficient for ML forecasting (see inspection report: 3 mock bookings, 7-day span, 1 completed, 0 cancelled, single city). This dataset provides a **separate deterministic synthetic ML training dataset** for prototyping demand forecasting, with a clear path to replace it with real aggregated booking data when Zolve has sufficient history.

**Real operational bookings** (`public.bookings` via `src/context/AppContext.jsx`, `src/components/customer/BookingModal.jsx`) remain the source of truth. **Synthetic ML training data** (`data/synthetic_demand_history.csv` + `data/synthetic_demand_features.csv`) is never written to the database.

| column | type | description |
|---|---|---|

| `rolling_14_day_mean` | float/NaN | mean of previous 14 days |

## Methodology (deterministic, prototype only)

Do NOT claim these represent real Indian service-market statistics.

- **Hash-based determinism:** Every stochastic element uses `hashlib.md5(f"{city}|{service_id}|{date}")` → uniform value, so output is reproducible and no global RNG state.
- **City baseline:** Metros weighted higher (Mumbai 1.45, Delhi NCR 1.40, Bengaluru 1.35 down to smaller hubs 0.80–0.88) — mimics population/service-area scale.
- **Service baseline:** Daily mean before city scaling e.g., Cleaning 8.0, Electrical 7.0, Plumbing 6.0, AC 6.0, Carpentry 5.0, Cooking 5.5, etc., tuned for plausible 1–15/day/city-service.
- **Trend:** `1.0 + day_index * 0.0015` → ~27% growth over 180 days (gradual expansion).
- **Weekday/weekend:** Service-specific: Cleaning 1.60 weekend /0.85 weekday, Gardening 1.45, Moving 1.70 weekend + 1.40 month-boundaries (1-3, 28-31), Society Event 1.80 weekend, AC 1.10 weekend, Electrical 1.08 weekday, etc.
- **Seasonal:** AC peaks May–June (`1.0 +0.45*cos((month-6)*π/6)` → 1.45 peak, 0.55 trough); Pest monsoon Jun-Sep 1.25; Gardening spring/monsoon 1.20; Painting monsoon 0.75, post-monsoon 1.25; Event festival Sep-Nov 1.40.
- **Controlled noise:** Uniform `±0.15` via hash (`deterministic_noise`).
- **Occasional spikes:** 2% rows 1.6–2.0×, additional 3% 1.3× (`deterministic_spike`) — simulates plumbing leak bursts, post-rain pest surge, etc.
- **Rounding & clamp:** `round(demand)` → int, `0 ≤ count ≤ 40`.

## Limitations

- Synthetic — must not be used as real customer data, pricing, or capacity planning evidence for SIH judging without disclaimer.
- No real seasonality/weather/holiday regressors (can be added as optional context features).
- No cancellations/refunds split (counts are for `CONFIRMED`→`SERVICE_COMPLETED` proxy).
- City spread is synthetic scaling, not census-derived.
- Single daily grain (not hourly); slot-level forecasting would need `scheduled_time` distribution.

## Model Training — Demand Forecasting (XGBoost, synthetic only)

> **Synthetic prototype demand data — evaluation does not represent real Zolve production accuracy.**
> Training uses ONLY synthetic data; `public.bookings` was never queried or modified.

**Script:** `scripts/train_demand_forecast.py`  
**Input:** `data/synthetic_demand_features.csv` (leakage-free lag/rolling already)  
**Target:** `booking_count`  
**Features:** `lag_1_day, lag_7_day, rolling_7_day_mean, rolling_14_day_mean, day_of_week, is_weekend, month, day_of_month, city, service_id`  

**Pipeline:**

1. Drop rows where any lag/rolling is `NaN` (first 14 days per `city/service_id` → 3,920 rows dropped, 46,480 remaining) — no imputation, avoids leakage (shift-1 rolling already leakage-free).
2. Sort by `date` and **time-based split** (never shuffle): unique dates sorted, 80% oldest → train, 20% newest → test.
   - Train: `2026-03-21` to `2026-07-30` (132 days, 36,960 rows)
   - Test: `2026-07-31` to `2026-09-02` (34 days, 9,520 rows)
3. Encode categoricals on train only: `OneHotEncoder(handle_unknown='ignore')` for `city` (20), `service_id` (14), `day_of_week` (7); numeric passthrough for `lag_1_day, lag_7_day, rolling_7_day_mean, rolling_14_day_mean, is_weekend, month, day_of_month`.
4. Model: `XGBRegressor(n_estimators=500, max_depth=8, learning_rate=0.05, subsample=0.8, colsample_bytree=0.8, reg_alpha=0.1, reg_lambda=1.0, random_state=42, seed=42, objective='reg:squarederror', tree_method='hist')` — reproducible (seed 42).
5. Evaluate on test: MAE, RMSE, MAPE (with clip `pred>=0`).

**Latest run (2026-09-03, synthetic):**

- Train rows: 36,960 | Test rows: 9,520
- Train `2026-03-21` → `2026-07-30` | Test `2026-07-31` → `2026-09-02`
- **MAE 0.7400, RMSE 1.2098, MAPE 12.73%**

**Outputs:**

- `models/demand_forecast_xgb.json` — XGBoost booster JSON (9.3 MB, `booster.save_model`)
- `models/demand_forecast_metrics.json` — metrics, split dates, feature list, disclaimer
- `data/demand_forecast_predictions.csv` — 9,520 rows `date,city,service_id,service_name,actual_booking_count,predicted_booking_count` (rounded 2-dec, clipped ≥0) sorted `date,city,service_id`

## Replacement with Real Data

Future pipeline (`scripts/prepare_forecasting_data.py`) is input-agnostic: point `--input` to a real aggregated CSV with same schema (`date,city,service_id,service_name,booking_count`) produced by:

```sql
SELECT scheduled_date::date AS date,
       city_normalized AS city,
       service_id, service_name,
       COUNT(*) AS booking_count
FROM public.bookings
WHERE booking_status IN ('CONFIRMED','SERVICE_COMPLETED')
GROUP BY 1,2,3,4
```

No code change needed beyond data source.
